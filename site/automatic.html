Build, review and authorize a hook

This workflow uses AutoHookJobRequester. Your wallet prepays the build and reserves the verdict fee. You select one reviewed artifact; anyone can then trigger its fixed oracle question. A valid true panel answer authorizes exactly that artifact for the official deployer. No owner binding transaction is needed.

Nothing is deployed by loading this page. Enter the operator-published contract addresses and select the correct wallet network. The panel and the existing IdentityMD v2 signer remain trusted. Public oracle vectors and local tests are available; no live Hooks Store success is claimed. An unanswered request can lose its spent fee. Unused reserve belongs to you.

Keep the wallet, network and form unchanged while an action is running. Changes require reconnecting. If a transaction hash is shown with an error, inspect it on the original chain before trying again: it may already have executed.

1. Prepay a build and verdict

At the published 0.5 IMD per action this prepays 1 IMD. Approve the quoted build fee plus reserve, then open the job. These are separate wallet transactions, each requiring native gas. A price increase can require a new approval. Build fees are spent immediately.

2. Inspect and commit the exact accepted reviewed build

Wait for the job to show Delivered, then compare the accepted source, independent review, compiler settings, bytecode and deployment context before committing. One candidate per job: this choice cannot be replaced. Worker publication grants no approval. The panel must independently verify acceptance and reproduction.

3. Trigger the oracle and prepare deployment

The build must be Delivered and the candidate committed. Wait eight native chain blocks after commitment, retry funding, renewal or top-up. Read status to check readiness, the live quote, remaining blocks and the reserve deadline (Unix seconds); Robinhood uses its own L2 block counter. Readiness requires an available positive quote within your reserve. The request spends that quote once, credits any surplus for withdrawal, and pins its fixed question. The asynchronous callback records true or false. A false result is terminal. A pending ask needs exceptional owner recovery after the full valid delivery horizon; a signed false cannot be cleared by expiry.

If your unspent reserve deadline has passed, renew the verdict window to keep the same candidate and ask, or cancel for a refund. Renewal is requester-only, requires Delivered with no pending or finalized verdict, transfers no tokens, and starts another eight-block wait. It cannot revive a cancelled reserve or a false verdict. It only costs native transaction gas.

If the verdict price rises, add funds to this committed, unspent ask using the job's original token. Your total reserve must stay within the current maximum for that original token, even after the protocol changes tokens. The build is already paid; the candidate and ask stay the same. A top-up also refreshes an expired reserve window and starts another eight-block wait. Cancelled, pending or finalized verdicts cannot be topped up.

After Passed, use python3 -m sdk.gated_deploy --binding-mode automatic to produce the unsigned deployment transaction for the exact candidate. The official contract checks it again. No result JSON is needed in automatic mode. See the workflow and operational runbook.
